串接範例細節 — mcab 的 front／fuse 序列與出貨板上還剩什麼 DEBUG 觀測面

本頁收 串接範例 的兩段細節:第 4 節 mcab 的 front 與 fuse 兩半的內部呼叫序列,以及第 7 節的完整內容(release build 的實測結論、板端監看迴圈、已知盲點);串接骨架、四個範例、layout_version 與整合檢查清單仍留在原頁。

4. mcab 的 front／fuse 呼叫序列

4.1 front 半的呼叫序列(重點在 far-FFT 共用)

1. skn_all_finite_f32(mic_interleaved, hop*4) && skn_all_finite_f32(ref, hop)   ← 唯一的輸入 NaN gate
2. de-interleave proxy channel → mic_lane
3. update_shared_delay(...)          ← duty 決策 + matched filter + ERLE watchdog
4. align_render(ref, delay)  → aligned_ref
5. if (delay.changed) 四 lane 各跑 aec_apply_external_realign(lanes[ch], delta)
6. for ch in 0..3:
     de-interleave lane ch
     ch==0 : aec_process_context(lanes[0], mic_lane, aligned_ref)
     ch!=0 : aec_process_context_shared_far_from(lanes[ch], mic_lane, aligned_ref, lanes[0])
     aec_get_res_context(lanes[ch], &context)
     bind_lane_view(&snapshots[ch], &context)          ← 借指標,不複製
7. front-valid 旗標置位(mcab_fuse 的序列閘)
四條 lane 這一 hop 看到同一個 aligned_ref 指標,所以其他三條可借用 lane 0 的 far 頻譜 → 4 次 far-FFT/hop 變成 1 次(混合 warm／soft realign 的 hop 改為各 lane 自算,見 pipeline_4ch_params)。這是 aec_process_context_shared_far_from() 存在的理由,也是它嚴格的 same-hop/same-reference 前提的由來。

4.2 fuse 半

1. front-valid 檢查                         ← 序列協定
2. mcab_weights_valid():逐元 isfinite + Σ|.| > 1e-12
3. fuse_contexts():coherent projection,四 lane far_power 一致性檢查,投影結果與 beamformed 頻譜的有限檢查
   (失敗 → MCAB_DSP_ERROR,mcab 已 reset)
   → 填 McabFrame(e/y/x/r2/cn/far_hop/formed_hop/max_dt/max_sat/all_converged/delay 旗標)

7. DEBUG:出貨板上還剩什麼

這一節只描述現況。要新增哪些 DEBUG 資訊的評估與提案,見 docs/debug_observability_zh_TW.md。

7.1 Release build 的實測結論

以 NO_STDIO=1 建出 archive 後用 nm 檢查,結果是一個很乾淨的分界:

類別存活消失
狀態快照(pull)aec_debug_status、aec_get_res_context、aec_get_linear_context、aec_linear_is_cancelling、aec_far_fft_real_compute_count、aec_get_mem_breakdown、anr_debug_status、anr_get_gain/_noise_psd、4ch 的全部 census/counter accessor(mcab_*_count()、mcab_duty_hops_*() 等)—
耗時函式在(回 0)全部數值(AecStageTiming／McabLastTiming)
Log / trace(push)—全部:aec_debug_set_level/_log/_frame、aec_debug_set_trace、AecDebugTraceRow 的 CSV 14 欄
錯誤碼全部—
Finite guards全部(不受任何開關影響)—
一句話:出貨板上唯一還活著的診斷面,是「主動 poll 的結構化狀態快照」。所有事件式(log／trace)與所有時間式(stage timing)觀測在 release 組態下歸零。任何 DEBUG 設計都必須建立在 pull 型快照上,而不是 printf。

7.2 可以直接照抄的板端監看迴圈

/* 每秒一次即可;三個 API 都是免費的(只讀引擎已維護的欄位) */
AecDebugStatus      a;  aec_debug_status(aec, &a);
AnrDebugStatus  n;  anr_debug_status(nr, &n);   /* nr = 你自己 anr_init() 的物件; NULL = 沒有降噪器 */

log("delay=%d conf=%.1f upd=%d erle=%.1fdB usable=%d conv=%d "
    "near=%.4f out=%.4f duty=%llu/%llu | nr_init=%d gain=%.1f/%.1fdB "
    "spp=%.2f noise=%.1fdB",
    a.delay_samples, a.delay_confidence, a.delay_updates,
    a.erle_windowed_db, a.usable_linear, a.filter_converged,
    a.near_power, a.out_power, a.duty_hops_run, a.duty_hops_total,
    n.initialized, n.mean_gain_db, n.min_gain_db, n.mean_spp, n.noise_floor_db);
讀到這樣通常代表
delay=-1 一直不變從未鎖定。檢查 ref 是否真的是送往喇叭的訊號、電平是否過低
erle 低但 conv=1濾波器收斂了但 echo 仍在 → 懷疑鎖到錯的 delay(早期反射),或非線性失真超出線性模型
duty_run/duty_total 接近 1.0 且長時間不降duty-cycle 未啟用(delay_est_period_s = 0,預設),或已啟用但 delay 一直不穩定而從未進入抽樣
nr_init=0 持續還在啟動 pass-through(前 num_init_frames 個 frame),此時完全不降噪是正常的
mean_spp 長期接近 0判定沒有語音 → 檢查電平或噪聲底是否估過高
noise_floor_db 隨語音一起爬升噪聲估計正在吸收語音 → 檢查 delta_db／alpha_d
三個常見誤判,先看這裡再懷疑演算法:
  • aec_get_last_timing() 回全 0 不代表很快——代表沒有用 PROFILE=1 建 library。而且函式不會告訴你它沒被啟用。
  • delay_updates 是 matched-filter 的更新總數,不區分「同一值重複確認」與「跳到新值」,不能當成 lock 穩定度指標。
  • near_power／out_power 是逐樣本的 EMA(alpha = 0.95^(16000/取樣率),16 kHz 為 0.95),不是瞬時值;duty_* 會被 reset() 清零。

7.3 現況的已知盲點(整合前先知道)

盲點實情
per-hop CSV trace 四條 pipeline 全部不可達AecDebugTraceRow 的唯一填寫點要求 cfg.enable_res == 1 且走 aec_process()。四條 pipeline 全部設 enable_res = 0 → dominant_nearend／saturated_echo／usable_linear／fullband_erle／gain_mean 這些沒有第二個出口的量,在產品組態下永遠取不到。只有 CLI aec_wav --debug-trace 拿得到
沒有層級式 logaec_debug_set_level()／aec_debug_set_log() 只把值存進 aec_debug.c 的靜態變數,library 內沒有任何讀取端,也沒有 emit 函式 → CLI 的 --debug-level／--debug-log 不會產生輸出
assert() 在出貨板上是活的四個 Makefile 沒有任何一個設 -DNDEBUG。suppression_gain.c 的 table-length assert 沒有 release-path fallback,失敗即 abort()——沒有回傳碼、沒有 log、沒有 hook 可攔
self-reset 不計數DSP_ERROR 路徑會內部呼叫 reset(),而 reset() 本身清掉所有 instrumentation(realign counters／duty census 全歸零)→ 一次 self-reset 之後「之前發生過什麼」在計數器上完全消失
delay lock 遺失不計數AecLinearContext.delay_state 與 generation 每 hop 可讀,但 AecDebugStatus 兩者都沒有 → 只 poll aec_debug_status() 的整合者看不到 lock 的丟失與重獲
NN fail-open 是靜默的三種 fallback 走同一條 else 分支、無區別、無計數 → 「NPU 掛了整段跑 identity」與「NPU 正常但某幾 frame 吐 NaN」從外部無法區分
4ch init 失敗一個字都不說mcab_init_ex() 的 8 項檢查與 lane／estimator 驗證任一失敗,以及 mcab_sample_beam_init() 失敗,都靜默回 NULL。mono 的 aec_init()／anr_init()／ac_istft_init() 也沒有任何診斷輸出,只回 NULL(大小查詢回 0);mono 沒有 descriptor 閘,所以「過小／未對齊／無效 config」三種原因從回傳值分不出來,要在呼叫前自己比對 *_get_mem_size() 與 pool 的大小和對齊
幾乎沒有 frame countermono(Aec、AnrDenoiser、AcIstft)與 NN stage 都沒有 frame counter 的 public accessor;4ch 的 helper 只在 McabSampleBeamInfo.frame_index 給(且 mcab_sample_beam_reset() 後歸零)→ 「這條 stream 到目前為止處理了幾個 hop」多半答不出來,遑論 xrun
mono 沒有內建 finite 守衛aec_process_context() 與 anr_process_gain() 輸入不檢、輸出不檢;輸出有限性要整合者自己用 skn_all_finite_f32() 檢查(example_board_adapter.c 這樣做,main.c 的 CLI 本身不做)。4ch 的輸入有檢查(mcab_process_front())
兩條 ULCNet 範例的 stage 沒有觀測面ulcnet_nn_stage 沒有診斷 accessor(沒有 model 呼叫計數、沒有 reprime 計數);mono 範例手上有 Aec handle,4ch 範例手上有 Mcab*(mcab_get_last_timing() 與計數器 accessor)與 helper 填的 McabSampleBeamInfo(DOA、BF 適應、delay 狀態)。stage 這一側的狀態(reprime、fail-open 次數)對整合者不可達
