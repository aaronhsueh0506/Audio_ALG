概要

整條鏈的共同格點規則：frame == FFT、hop = fft/2（50% overlap）、無 transform zero-padding、bins = fft/2+1。各層各有自己的預設與白名單， 本頁把它們放在同一張表；另外收錄三件跨模組最容易踩的 framing 事實： 重建路徑一律 periodic sqrt-Hann、PBFDKF 線性路徑的矩形窗例外、 centered 與串流（center=False）framing 在穩態逐 bit 等價。

視窗慣例：重建路徑一律 periodic sqrt-Hann

所有「會被合成回時域」的路徑（分析與合成兩側）用同一個公式，denominator = block 長度 N（periodic，非 symmetric）：

w[k] = sqrtf(0.5 * (1 - cos(2*pi*k / N)))     k = 0..N-1
使用點程式碼

mono 範例合成窗pipelines/mono_aec_nr_res/main.c：main 自己初始化的 AcIstft 借用 AEC 的窗表（初始化後的 Aec 經 aec_synthesis_window() 取得；AcStftConfig.window 借入，不另切）
4ch 範例合成窗pipelines/4ch_aec_bf_nr_res/mcab_static.c：main 自己初始化的 AcIstft 自帶的窗表（ac_window_build()，audiolib/common/src/audio_window.c）

sqrt-Hann 分析 × sqrt-Hann 合成 = Hann，在 50% overlap 下滿足 COLA， 合成端不需 window-envelope 除法（dfn2_process.h 檔頭的 framing 契約： plain overlap-add，AC_OLA_ACCUMULATE）。 例外是 torch.istft 語意的 ULCNet WOLA：它照 torch 做窗平方包絡正規化 （AC_OLA_ENV_NORM 的 env 累加器），結果相同、簿記不同。

STFT／ISTFT 組幀家族（audio_stft.h）

上表所有呼叫點都經 audiolib 的 AcStft／AcIstft；差別只在兩個旋鈕： 分析的 center（0 = 每次 push 恰一幀、零歷史起算；1 = torch center=True、reflect 前綴）與合成的 ola 模式（AC_OLA_ACCUMULATE = acc += ifft×w、每幀吐一個 hop；AC_OLA_ENV_NORM = 另累加 w×w、除以包絡、第一幀不吐）。頻譜縮放由 DFN2／DFN3／RNNoise-ERB 用：spec_scale = grid.stft_scale（1/√n_fft）；DFN2／DFN3 的 ispec_scale = grid.stft_unscale（√n_fft）， RNNoise-ERB 的 ispec_scale 保持 1.0（√n_fft 已折進 rnnoise_apply_gains()）。出貨 grid（48 k／1024）的值是 1/32 與 32，皆 2 的冪、乘法不進位； n_fft 為 4 的次方（256、1024、4096）時精確，512 為四捨五入的 float。縮放恰為 1.0f 時略過乘法。 DfnResStage／DfnRateBridge 吃 audio-scale 頻譜、自己乘 stft_scale／stft_unscale，呼叫端的 AcStft／AcIstft 保持 1.0。

AC_OLA_ACCUMULATE 把每幀累加進已歸零的 acc 再吐出；若另一個實作改成「前一幀尾巴直接 copy」，兩者數值只可能差在零的符號 （-0.0 對 +0.0），其他位元相同。窗公式 sqrtf(0.5f - 0.5f*cosf(...)) 與 sqrtf(0.5f*(1.0f - cosf(...))) 在 float 下逐 bit 相同 （0.5f 的乘法是精確的縮放）。

PBFDKF far_spec 矩形窗例外

線性濾波路徑沒有分析窗。PBFDAF/PBFDKF 是 overlap-save 結構： far/near 的 block（= 2×hop 原始樣本）直接進 RFFT—— pbfdkf.c 的 rfft_padded(p, p->far_buffer, blk, p->far_spec) 與同樣的 near_spec——等效矩形窗。輸出取 echo_time[hop:block] 有效半段、error_spec 由 zero-pad 的有效 hop 重建，全程無窗。sqrt-Hann 只出現在供 RES/後級分析用的 error_spec_windowed（sqrt-Hann×near − echo_spec）。 另有 td_window（IR 時域約束窗：在 [0, hop) 為 1、[hop, fft_size) 為 0，保留每個 partition 的因果半、清掉其餘，避免 wrap-around 能量漏進下一個 valid hop），作用在濾波器係數不是訊號。

centered framing 與串流（center=False）framing

AINR DFN2 的 C 是 center=False 串流（dfn2_process.h 檔頭的 framing 契約：與訓練 graph 的 center=True 只差一個 clip 的第一幀）， Align-ULCNet 的 C 出貨路徑也是 center=False rolling 分析，與 torch center=True 的穩態幀逐 bit 重合（ulcnet_process.h 檔頭 + docs/align_ulcnet_embedded_streaming_design_zh_TW_01_state_wola_delay.md §7）。

穩態幀為何重合（逐 bit）：本 grid 下 win = n_fft、hop = win/2、同一 sqrt-Hann 窗。centered 第 k 幀以樣本 k·hop 為中心，覆蓋 [k·hop − win/2, k·hop + win/2) = [(k−1)·hop, (k+1)·hop)； non-centered 第 k−1 幀覆蓋 [(k−1)·hop, (k−1)·hop + win)——同一段樣本、 同一張窗 → 頻譜逐 bit 相同，差別只剩幀編號。因此：

  • 兩種 framing 的 STFT→NN→ISTFT 鏈穩態 I/O 延遲都是同一個 1 hop （WOLA 收尾本來就要等下一幀；centered 的半窗 lookahead 藏在其中）。 改 past-only framing 拿不到任何延遲收益。
  • 真實差異只有 (a) 串流開頭第一幀：reflect 前綴 vs 零填冷啟動（影響 recurrent-state start transient）；(b) 檔案級評測的幀數/邊界；(c) 幀時間戳 語意。checkpoint 的 feature-time contract 因此不能靜默改 framing——換 framing 是輸入分佈變更，須 A/B。
  • C 實作佐證：AcStft（center 1）的排程是 push#0→0 幀、 push#1→2 幀（frame0 含 reflect 前綴 + frame1）、之後每 push 1 幀；輸出端 AcIstft（ENV_NORM）frame#0→0 樣本（半窗 trim）、之後每幀 256 樣本——與 dfn2 的 center=False 串流輸出排程逐 hop 相同。

ULCNet 的兩種分析排程並存，出貨路徑分兩派。 AcStft 的 center 0（應用端以 ac_stft_config_default() 的預設建立， 契約在 lib/aiaec/ulcnet/ulcnet_process.h）是 rolling 分析： 從第一次 push 起每次恰好一幀（第一幀的前半段是被歸零的 history）， 且與 center 1 對同一個 pushed hop 所發的 最後一幀逐 bit 相同——centered 排程只是多了開頭那個 reflect 前綴幀。 上面的穩態等價性因此原封不動地成立，換掉的只是幀編號與串流開頭。 同一個 AcStft 不可混用兩種 center（center 在建立時固定）。

  • 用 center 0：三支前後處理 class 的 framing 契約 （ulcnet_prepost／deepvqe_prepost／dfn2_prepost 都是 center=False）、4ch ULCNet pipeline 的 far 分支，以及 mono ULCNet pipeline 兩路皆是 （pipelines/ulcnet/ulcnet_nn_stage.c 的 ac_stft_push_planar(err_analysis / far_analysis, …)）——因為它們要和 AEC/BF seam 自己的頻譜（一 hop 一幀、從 hop 0 起）配對，一手已經是那種幀時， 另一手就得用同一個排程才對得上 hop；mono 的 error/far 兩路本來就同 hop 推入，換成 rolling 排程後兩者天生 hop-locked，不需再靠 centered 排程的 0/2/1 發射對齊。
  • 用 center 1：只剩 Python parity gate （AIAEC/tests/test_ulcnet_process_c.py）與 test_ulcnet_prepost_c.py 的 equiv 案例，兩者都需要 0/2/1 排程本身作為比對基準，不代表任何出貨 pipeline。
